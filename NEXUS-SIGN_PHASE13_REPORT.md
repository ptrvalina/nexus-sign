**Граница исполнения: `execute(paymentId)` — единственная функция, которая может дойти до платёжной системы.** Шаги одной попытки:

1. Захват платежа в журнале банка (`bank_executions`): аренда и `claim_id`, финальные состояния защищены триггером.
2. `bank-commit-request` у Auth Core — только предусловие. 4xx — `REFUSED`; сетевая ошибка, 5xx или тайм-аут — `HELD`.
3. Доказательство и цепочка от Auth Core. Утверждения банка, сохранённый head и записанные условия — из БД банка. На них выполняется `bankExecutionDecision`.
4. Финальная проверка в одной транзакции: строка доверия credential читается `FOR SHARE` и должна быть `APPROVED` для этого клиента, затем переход `CLAIMED → EXECUTING` при действующем `claim_id`.
5. Платёжный адаптер с одноразовым разрешением, выданным на ровно этот заказ, и идемпотентным ключом `bankTransactionReference`.
6. `EXECUTED` и продвижение head — в одной транзакции; Auth Core сообщается `COMMITTED`.

Любая ошибка до шага 5 переводит платёж в `HELD`. Ошибка на шаге 5 даёт `OUTCOME_UNKNOWN`. Следующая попытка выполняет `lookup` по ключу (`EXECUTED` или `REVIEW`), повторного `execute` нет.

**Реестр доверия банка** (`postgresTrustStore.mjs`, только в БД банка):

- `bank_trust_statements` — подписанные утверждения, только добавление; при записи проверяются ключами доверия банка;
- `bank_credential_trust` — привязка credential к одному клиенту, отзыв окончателен (триггеры);
- `bank_chain_heads` — head продвигается только вперёд;
- `bank_payments` — ожидаемые условия; одна авторизация — один платёж (`UNIQUE`);
- `bank_executions` — журнал исполнения.

Ключи проверки доказательств и ключи доверия банка задаются конфигурацией и из экспорта Auth Core не берутся.

Формат утверждений и протокол фазы 12 не менялись. Новой криптографии нет.

## 5. Что осталось непроверенным

- **Интеграция в реальный банковский backend и платёжную систему** — их нет в репозитории (R-22).
- **Пути исполнения банка за пределами репозитория:** операторские действия, API, джобы, повторы, обработчики webhook, админ-инструменты. Каждый должен вызывать `execute()`; проверить это может только банк.
- **Разрешение адаптера** защищает внутри одного процесса. Код банка, у которого есть сырой адаптер, может обойти его.
- **Нет атомарности между БД банка и платёжной системой** (R-24). Защиту дают идемпотентный ключ, `lookup`, `OUTCOME_UNKNOWN` и `REVIEW`. Отзыв после финальной проверки этот платёж не останавливает, только сообщает о нём.
- **iOS: NOT RUN.** `signingKeyFingerprint()` и тест по векторам не скомпилированы. iOS-контроллер звонков не менялся и не запускался.
- **Android:** нативная сборка — NOT RUN (нет Android SDK, Maven отвечает 403). Устройства — NOT RUN. Исправления двух гонок `VerificationCallController` сохранены, conformance 20 из 20.
- **Вне модели:** отказ в обслуживании со стороны Auth Core; компрометация самого backend банка или его приложения; аттестация устройства, которую проверяет только Auth Core.
- **SoftHSM вместо HSM поставщика; нет независимого аудита.**

## 6. Какие внешние действия нужны для допуска к выпуску

1. Встроить `bank-integration` (или реализацию того же контракта) в backend пилотного банка:
   - все пути к исполнению — через `execute()`;
   - сырой адаптер недоступен остальному коду;
   - тесты банка на каждый свой путь исполнения.
2. Подтвердить с платёжной системой банка идемпотентность по ключу и `lookup`. Описать процедуру сверки для `OUTCOME_UNKNOWN` и `REVIEW`, настроить оповещения по `HELD`, `REFUSED` и `REVIEW`.
3. Ключ доверия банка — в HSM банка. Отдельная БД реестра с резервным копированием. Ключи доказательств закреплены по протоколу key ceremony. Head сохраняется из каждого `evidence.appended`.
4. Собрать и проверить iOS и Android на Mac/Xcode и с Android SDK, на устройствах. Сборки должны выдавать `signingKeyFingerprint()`.
5. Испытания на HSM поставщика; восстановить воспроизводимую цепочку поставок (lockfile).
6. Независимая оценка безопасности; юридическая и регуляторная приёмка.
