## 2. Изменения

### 2.1. Модель

- **Отдельная схема `bank`.** Её владелец не суперпользователь и используется только для миграций. `PUBLIC` не имеет прав на схему, таблицы, последовательности и функции.
- **Ни у одной прикладной роли нет записи в таблицы.** Нет `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, прав на последовательности, `CREATE` в схемах и `TEMPORARY` в БД.
- **Любое изменение выполняет функция `SECURITY DEFINER` владельца** с `SET search_path = pg_catalog, pg_temp` и полностью квалифицированными именами. Каждая роль выполняет только свои функции: boundary, gateway, registry, operator.
- **Автомат состояний знает, какая функция делает переход.** Функция объявляет себя (`bank.via`) непосредственно перед изменением одной строки. Триггер принимает только тройки (откуда, куда, функция) из `bank.allowed_transitions`, гасит объявление и пишет строку журнала: откуда, куда, попытка, функция, `session_user`. Ни одна роль не пишет журнал. Изменять, удалять и очищать его не может никто, включая владельца.
- **Одобрение строится из данных самой БД.** `bank.approve(payment, attempt, evidence, lease_ms)` берёт учётные данные из evidence. Затем проверяет, что evidence относится к авторизации, клиенту, референсу и подписанным условиям именно этого платежа. Строку реестра читает `FOR SHARE`, что сериализует её с отзывом. Хеш заказа вычисляет сама БД. Одобрение используется один раз.
- **Подписи проверяются дважды вне БД.** В PostgreSQL нет ECDSA. Граница выполняет решение банка до `bank.approve`. Шлюз повторяет его на сохранённом evidence и реестре на момент одобрения (`approval_registry_id`), прежде чем выполнить `bank.submit`. Точка фиксации отзыва осталась на `APPROVED`.
- **Результат провайдера записывает только шлюз** (`bank.report`) и только для своей попытки. Граница может лишь перевести платёж в сверку или ручную проверку, но не в конечное состояние.
- **Ручную проверку завершает оператор под своим логином.** `resolved_by = session_user`; имя не передаётся аргументом.
- **`installSchema`:**
  - сначала отзывает все права ролей, в том числе на таблицы фазы 14 в `public`;
  - задаёт права по умолчанию для объектов, созданных позже;
  - отказывает ролям-суперпользователям и членам роли владельца;
  - `privilegeMatrix()` читает фактические права из каталога.

Решения: D-049…D-052. Документ с полным описанием: `docs/security/bank-database-authorization.md`.

### 2.3. Изменённое поведение (честно)

- **Падение границы после отправки ничего не теряет.** Шлюз уже записал ответ провайдера. Ожидание в тесте EP «crash at each transition» для шага `submitted` изменено: было `SUBMITTED`, стало `EXECUTED`.
- **Head цепочки продвигается отдельным вызовом после `EXECUTED`.** Он больше не в одной транзакции с `EXECUTED` (R-27).
- **Устранены способы, которые работали в фазе 14.** Тесты EP/EB, которые ожидали ошибку триггера на прямой `UPDATE` от роли границы, теперь ожидают `permission denied`. Для владельца добавлены отдельные проверки.

## 4. Функции `SECURITY DEFINER`

Все 19 функций:

- принадлежат владельцу схемы;
- имеют `search_path = pg_catalog, pg_temp`;
- обращаются к объектам схемы только через `bank.`;
- не исполняются `PUBLIC` (DA 13 проверяет всё это по `pg_proc`).

По каждой функции в `docs/security/bank-database-authorization.md`, раздел 4, описаны: владелец, `search_path`, права `EXECUTE`, используемые таблицы, допустимые аргументы, инварианты и исключённые тестами обходы. Кратко:

| Функция | Роль | Главное |
|---|---|---|
| `approve` | boundary | попытка, живая аренда, границы аренды, привязка evidence к платежу и подписанным условиям, учётные данные из evidence в реестре для этого клиента, не отозваны, есть заявление; хеш заказа из БД; один раз; `FOR SHARE` против отзыва |
| `claim`, `refuse`, `hold`, `mark_unknown`, `mark_review` | boundary | только своя попытка, только перечисленные переходы, ни одного конечного состояния кроме `REFUSED` |
| `create_payment`, `attach_authorization`, `keep_head`, `add_finding` | boundary | проверка формы; уникальность; head только вперёд; `recorded_by = session_user` |
| `submit_basis`, `submit`, `resubmit` | gateway | `APPROVED` или `RECONCILING`, своя попытка, живая аренда, хеш заказа не изменился, один раз |
| `gateway_refuse`, `report`, `operation_for_lookup` | gateway | только своя попытка; ничего из конечного состояния; lookup только после отправки |
| `approve_credential`, `revoke_credential` | registry | один клиент на учётные данные; отзыв окончателен; возвращает платежи в обработке |
| `resolve_review` | operator | только `REVIEW`; заметка обязательна; `resolved_by = session_user` |

**Чего БД не решает.** Подписи на evidence и заявлениях она не проверяет. Заявление без подписи, сохранённое ролью реестра, нигде не засчитывается: его проверяют граница и шлюз (DA 6, EB). `bank.via` — метка, а не полномочие: значение имеет только для того, кто может обновлять таблицы, а это только владелец (DA 3).

**Чистая БД, переустановка, обновление.**

- Администратор один раз выполняет `DATABASE_HARDENING`.
- Повторная `installSchema` убирает лишние гранты: `UPDATE`/`INSERT` на `executions`, `USAGE` на последовательности, чужие функции, `EXECUTE` для `PUBLIC`.
- Права на таблицы фазы 14 в `public` тоже снимаются.
- Новые объекты никому не выдаются (DA 14).
- **Данные фазы 14 не мигрируются:** это остаётся задачей банка.
