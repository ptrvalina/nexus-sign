## 1. Формальная модель состояний

Документ: `docs/architecture/payment-state-machine.md`. Для каждого перехода там описаны предусловия, транзакционные изменения в БД, внешние вызовы, поведение при сбое, повтор и восстановление после перезапуска.

- Состояния платежа: `CREATED` → `AWAITING_AUTHORIZATION`.
- Состояния исполнения: `CHECKING`, `HELD`, `APPROVED`, `SUBMITTED`, `PENDING_PROVIDER`, `OUTCOME_UNKNOWN`, `RECONCILING`, `REVIEW`. Конечные: `EXECUTED`, `PROVIDER_FAILED`, `REFUSED`.
- Таблица допустимых переходов проверяется триггером БД для **любой** роли. Каждый переход пишется в журнал (только добавление) вместе с ролью, которая его выполнила.

Разделены четыре факта:

1. подтверждение клиента — `VERIFIED` в Auth Core;
2. решение банка — `APPROVED`;
3. отправка команды — `SUBMITTED`, пишется шлюзом **до** вызова провайдера;
4. подтверждённое исполнение — `EXECUTED`, только по ответу провайдера или lookup.

`COMMITTED` в Auth Core — лишь отчёт банка после `EXECUTED`, а не доказательство перевода.

**Точка фиксации отзыва — переход `CHECKING → APPROVED`.** Отзыв, пришедший позже, платёж не отменяет: `revoke()` возвращает его как находящийся в обработке.

**Межпроцессная защита (F1).** Полномочие на отправку — строка `APPROVED` в БД банка для одного attempt ID и одного хеша заказа. Это не токен и не объект в памяти.

- Шлюз — отдельный процесс со своей ролью PostgreSQL. Роль не имеет прав на таблицы и может только вызывать `bank_submit` и `bank_resubmit` (`SECURITY DEFINER`).
- `bank_submit` отправляет **сохранённый** заказ, только для попытки, держащей `APPROVED`, и только один раз (`APPROVED → SUBMITTED` под блокировкой строки).
- Шлюз сверяет заказ с хешем, привязанным при одобрении.
- Роль границы не может выставить `SUBMITTED`: триггер разрешает это только владельцу, под которым работают функции.
- Вызывающие шлюз аутентифицируются по mTLS со списком разрешённых имён сертификатов.

Всё это стандартные механизмы; собственного криптопротокола нет.

**Контракт провайдера (F3).** Возможности объявляются явно: `providerCapabilities: { idempotentSubmit, lookup }`, по умолчанию обе false.

- **Без lookup:** неизвестный исход уходит в `REVIEW`.
- **Без идемпотентности:** ответ «не найден» уходит в `REVIEW`.
- **С обеими гарантиями:** повтор с тем же `operationId`.

Повторной отправки только из-за отсутствия ответа нет.

## 5. Атаки и сбои: воспроизведены и заблокированы

Номера — тесты `bank-execution-processes` (EP) и `bank-execution-boundary` (EB). Подробная таблица — в модели угроз, раздел «Phase 14».

- **Межпроцессный обход:** без сертификата, с сертификатом другого CA, с сертификатом другого сервиса, без `APPROVED`, из `CHECKING`, с attempt ID попытки `RECONCILING`, с чужой попыткой, повторно, с изменённой суммой в запросе. Провайдер не вызывается или получает сохранённый заказ. Роль границы не может выставить `SUBMITTED`, роль шлюза не имеет доступа к таблицам.
- **Провайдер.**
  - pending → `PENDING_PROVIDER`, затем после урегулирования `EXECUTED`;
  - failed → `PROVIDER_FAILED` без повтора;
  - бессмысленный ответ, потерянный ответ, ответ после тайм-аута → `OUTCOME_UNKNOWN`, затем lookup, один перевод;
  - процесс шлюза убит после исполнения → восстановление, один перевод;
  - неидемпотентный провайдер → никаких повторов, один перевод;
  - нет lookup или «не найден» без идемпотентности → `REVIEW`, решение человека с именем и пометкой;
  - расхождение локального состояния и провайдера → находка, состояние не меняется.
- **Барьеры и сбои.**
  - отзыв на `checking` и `beforeApprove` → `REFUSED`; на `approved` → исполнено и сообщено как находящееся в обработке;
  - падение на каждом переходе → следующая попытка завершает, один перевод;
  - два экземпляра, один удерживается на барьере;
  - 40 запросов на 4 экземплярах вместе с job сверки (дополнительный стресс-тест);
  - замена устройства во время проверки;
  - гонка chain head: head не откатывается, БД отвергает откат.
- **Скомпрометированный Auth Core.**
  - ответы с ключами, реестром и head игнорируются;
  - ошибка в ответе ведёт к отказу;
  - повтор одобрения после отзыва отклоняется;
  - корректно подписанный webhook для неодобренного ключа → `REFUSED`;
  - повторные webhook → одно исполнение; поддельные → 401;
  - доступа к шлюзу у Auth Core нет: TLS отказывает.

## 6. Остаточные риски и внешние зависимости

- **R-22.** Интеграция в реальный backend банка не выполнена; пути исполнения банка за пределами репозитория не проверены.
- **R-24 (BLOCKED).** Единственность исполнения у реального провайдера зависит от его идемпотентности по `operationId` и авторитетного lookup. Контракта нет. Без этих гарантий автоматическое единственное исполнение невозможно: только `REVIEW`.
- **R-25.** Держатель роли и сертификата границы — это и есть точка решения банка. Держатель учётных данных владельца схемы может отключить триггеры. mTLS только аутентифицирует вызывающего.
- **Вне модели:** компрометация провайдера, backend или приложения банка; отказ в обслуживании; аттестация устройства, проверяемая только Auth Core.
- **NOT RUN:** нативные SDK, устройства, iOS, HSM поставщика, независимый аудит.
