## 2. Итог проверки исходной гипотезы

**Гипотеза подтверждена.** До исправления серверная проверка при `bank-commit-request` и флаг `confirmed` в `GET` сравнивали запечатанный payload со строкой `authorization_requests`. При этом колонки `nexus_id` и `credential_id` самой строки `evidence_records` с payload не сравнивались. Если изменить эти колонки при неизменном payload, печать остаётся действительной, и коммит принимался: 202, `bank_transaction_state = COMMIT_REQUESTED`.

Ответы по пунктам:

| Вопрос | Ответ (на `2df8754`) |
|---|---|
| `record.nexusId` против `payload.nexusId` | **Сервер: нет.** Сравнивались `payload.nexusId` и `authorization_requests.nexus_id`. Verifier сравнивал. |
| `record.credentialId` против `payload.credentialId` | **Сервер: нет. Verifier для schema 3: нет.** Сравнивался только `payload.credentialId` со строкой авторизации. |
| `operationId`, `deviceId` и прочие идентификаторы | Колонок `operation_id` и `device_id` в схеме нет. Роль ключа поиска играет `authorization_id`: запись выбирается по колонке, затем `payload.authorizationId` сравнивается с авторизацией, так что колонка проверялась транзитивно. `record_type` фильтруется в запросе и сверяется с payload. `chain_sequence` и `previous_evidence_hash` проверялись (фаза 10). `seal_key_id` и `schema_version` неявно использовались проверкой печати; verifier сверял `seal_key_id`, но не `schema_version`. `transaction_reference`, `signature` и прочие копии в решениях не участвуют. |
| Авторитетные поля для решения | Строка `authorization_requests`: условия неизменяемы благодаря триггеру. Запечатанный payload: его доказывает HSM-печать. Строка `credentials` вместе с запечатанной записью `CREDENTIAL_ENROLLED`. |
| Влияние метаданных | Да, на выбор доказательства. Колонка `nexus_id` определяет, к чьей цепочке относится запись: `GET /nexus-identities/{id}/evidence` и поиск предшественника. ## 5. Проверки метаданных, payload, HSM-печати и подписи устройства

Порядок проверки при коммите (`authorizationEvidenceProblem`, в транзакции под `FOR UPDATE` строки авторизации):

1. Ровно одна запись `AUTHORIZATION` с этим `authorization_id`.
2. HSM-печать: `schema_version = '3'`; `sha256(canonicalJson(payload)) = evidence_hash`; ключ по `seal_key_id` известен; подпись ECDSA P-256 верна.
3. Привязка: `payload.recordType`, `authorizationId`, `credentialId`, `nexusId`, `canonicalPayloadHash` равны строке авторизации.
4. Позиция: `payload.chainSequence` и `previousEvidenceHash` равны колонкам; предшественник `(nexus_id авторизации, seq-1)` имеет этот хеш.
5. **Новое: все колонки, повторяющие запечатанные значения, равны им.**
6. `signedPayloadBase64` совпадает с каноническими байтами хранимых условий; метод подтверждения совпадает со строкой.
7. Код без подписи (`OFFLINE_CODE`) допускается только при `immediate`.
8. Регистрация: запись `CREDENTIAL_ENROLLED` прочитана сейчас; её печать (возможно, из кеша по точному хешу и подписи), payload и **колонки** проверены; ключи credential равны запечатанным.
9. `enrolmentEvidenceHash` совпадает; ключ устройства в payload равен зарегистрированному; подпись ECDSA устройства над каноническими байтами верна.

`confirmed` в `GET` вычисляется той же функцией. Verifier независимо проверяет хеш, печать (по ключу, названному записью), метаданные (включая новые поля), подпись устройства и связь с регистрацией.

Каноническое представление идентификаторов не нормализуется. Это сознательно: UUID и NEXUS ID выпускаются Auth Core в канонической форме, а парсеры проверяют формат с фазы 10. Различие регистра или пробелов поэтому считается несовпадением, а не приводится к равенству.

Границы транзакции и изоляция:

- `requestCommit` — одна транзакция READ COMMITTED: `FOR UPDATE` строки авторизации, `FOR SHARE` строки идентичности, затем повторная проверка доказательства в той же транзакции (точка принятия решения), затем `UPDATE PENDING → COMMIT_REQUESTED`.
- Записи доказательств не блокируются. Роль приложения изменить их не может (REVOKE и триггер), а вставка копии упирается в `UNIQUE(authorization_id)`.
- Изменение записи владельцем после принятого 202 ретроактивно на коммит не влияет. Последующий `GET` покажет `confirmed: false`, verifier покажет нарушение; для этого банк и сверяет экспорт.
- Строка credential при коммите не блокируется. Замена устройства и восстановление блокируют идентичность (`FOR UPDATE`) и сериализуются с коммитом. Отзыв через API банка идентичность не блокирует, поэтому пересекающиеся запросы упорядочиваются, как в MB 11. Это допустимый сериализуемый порядок, а не обход: запрос, начатый после завершения отзыва, отклоняется.

Разделение гарантий:

- **NEXUS-SIGN** гарантирует, что для одной авторизации принимается не более одного `COMMIT_REQUESTED` (одна ссылка, идемпотентно) и только при действительном доказательстве на момент решения.
- **Однократное движение денег** гарантирует только банк: исполнение один раз на `bankTransactionReference`, только после 202, с отчётом `bank-commit-result`. Блокировка одной строки в Auth Core от двойного исполнения на стороне банка не защищает.

## 9. Оставшиеся угрозы и ограничения

- **Компрометация Auth Core не устранена.** Процесс, держащий HSM-сессию, может запечатать регистрацию ключа злоумышленника и подтверждения его ключом, согласованные во всём, что проверяют сервер и verifier.
- Банк должен сверять сам:
  - `credentialId` каждого исполняемого подтверждения со списком credential, которые банк сам принял для клиента (шаг 5 руководства);
  - chain heads из `evidence.appended` (`--expect-head`);
  - экспорт verifier-ом с ключами доказательств, полученными вне Auth Core.

  Регистрация, которую банк не инициировал, — инцидент.
- Для отдельной архитектурной фазы:
  - одобрение регистрации вне Auth Core (контрподпись банка или собственная проверка аттестации банком);
  - якорение ключей доказательств и chain heads вне контроля Auth Core;
  - проверка цепочек аттестации в verifier.
- Владелец БД с отключёнными триггерами по-прежнему может сделать отказ в обслуживании: испортить запись, после чего коммит этой авторизации невозможен. Обнаруживается, но не предотвращается.
- Удаление последней записи цепочки без сохранённых банком heads невидимо.
- SoftHSM ≠ HSM поставщика. iOS не собран. Нативные сборки и тесты на устройствах не выполнены. Цепочка поставок не воспроизводима (нет lockfile, FI-009). Нестабильный SDK call conformance (раздел 6) открыт.
- Тесты запускались от суперпользователя PostgreSQL; разделение ролей проверяет только `db-roles.test.mjs`.
- Успешные тесты — не независимый аудит. **Готовность к production не заявляется.**
