# Threat model

Scope: Auth Core, the iOS SDK and the Android SDK as deployed by a bank, with the bank's API gateway, HSM, database roles and attestation configuration. The [sandbox](../../sandbox/README.md#security-boundary) is out of scope and is not a production system. This page describes release 2.0.0-rc.2. It is an engineering baseline, not a certification artifact; certification, regulatory compliance and independent assurance are the responsibility of the deploying bank.

The controls are specified in the [protocol specifications](../protocol/README.md), [device attestation](attestation.md), [HSM and key management](hsm-key-management.md) and the [configuration reference](../operations/configuration.md).

## Production requirements

`NODE_ENV` must be set explicitly. With `NODE_ENV=production`, Auth Core refuses to start unless the following hold (`auth-core/src/config/productionPosture.ts`, [production blockers](../operations/configuration.md#production-blockers)):

1. HSM: a PKCS#11 HSM, with the token and the evidence key selected by label (and `CKA_ID` when needed); the software HSM is for development only.
2. Attestation: device attestation is verified server-side (App Attest; Play Integrity with Android Keystore key attestation) for at least one platform. With Android configured: a key security policy other than `ALLOW_SOFTWARE`, the app signing certificate digests, a locked bootloader, Google's attestation status list and a device verdict stronger than `MEETS_BASIC_INTEGRITY`.
3. Transport encryption: PostgreSQL and Redis connections use TLS with certificate verification.
4. Gateway mTLS: ingress for bank systems goes through a bank-controlled mTLS gateway whose addresses are listed in `TRUSTED_PROXY_IPS`.
5. Webhook egress: HTTPS only, an explicit host allow-list, `WEBHOOK_SECRET_ENCRYPTION_KEY` set.
6. Admin console: `Secure` session cookie, TOTP required, `ADMIN_SECRET_ENCRYPTION_KEY` set.
7. `ALLOW_INSECURE_DEVELOPMENT` is not set.

Outside production, the software HSM, attestation off, the gateway check off or admin MFA off need `ALLOW_INSECURE_DEVELOPMENT=true`, so a mislabelled deployment does not run without these controls by accident. Master keys and TTL bounds are validated at startup in every environment. The checks confirm that settings are present, not that the infrastructure behind them behaves as required (for example, that the gateway overwrites its headers).

## Invariants

These do not depend on configuration:

1. Every enrolled device signs each request with a hardware authentication key; no bearer token exists for an enrolled device ([device authentication](../protocol/device-authentication-and-offline-confirmation.md)). The only bank-issued mobile token is a single-use `BOOTSTRAP` token for enrolment. Suspended or revoked identities, and identities of a disabled bank client, are refused on every mobile request.
2. Devices enrol only through `POST /v1/mobile/bootstrap` or recovery, with attestation per policy; the bank API cannot register or rotate device keys. Only P-256 public keys are accepted.
3. A device is never replaced silently: a `BOOTSTRAP` token for an identity with an enrolled device requires the bank's replacement authorization, and the replacement is audited, sealed, reported by webhook and announced on the old device where secure push is used. An identity has at most one `ACTIVE` credential.
4. Authorizations are transaction-bound and signed by a hardware-backed device key. The device verifies the signed bytes before it displays or signs them, and displayed text cannot contain control, bidi, zero-width, separator or lone surrogate characters.
5. Verification is atomic and single use, with at most five signature or offline-code attempts per authorization. It re-checks the verification plan, the expiry, the credential key and the canonical bytes under row locks, so a concurrent step-up escalation cannot be skipped.
6. A commit request is accepted only while the identity and the confirming credential are `ACTIVE` and within `BANK_COMMIT_MAX_AGE_SECONDS` of the confirmation.
7. The recovery phrase never leaves the device, and no stored value completes a recovery ([recovery protocol 2](../protocol/recovery-protocol-v2.md)). Protocol 1 and its stored verifiers no longer exist.
8. Evidence is hash-linked, numbered per identity, sealed by the HSM, append-only and verifiable offline, including the customer's signature and the sealed enrolment of the key that produced it ([evidence format](../protocol/evidence-format.md)).
9. Credential keys and recovery keys are not taken from the database on trust: before use they are compared with their HSM-sealed records, and a mismatch is refused and audited as `integrity_violation`.
10. The database enforces the lifecycles of authorizations, bank transactions, credentials and identities, keeps a credential's keys and an authorization's bound transaction immutable, and keeps `evidence_records` and `audit_logs` append-only ([state machines](../architecture/state-machines.md)).

## Assets

| Asset | Where it lives | Why it matters |
|---|---|---|
| Device signing key | Secure Enclave or Android Keystore, not exportable; usable only after biometric authentication | Signs the canonical authorization bytes (the customer's proof of intent) and the recovery setup |
| Device authentication key | Secure Enclave or Android Keystore, not exportable | Signs every mobile request after enrolment |
| Sealed enrolment of each credential | `CREDENTIAL_ENROLLED` record in `evidence_records` | States which keys the device enrolled and the attestation that admitted them; Auth Core uses a credential's keys only if they match it |
| Offline confirmation key `K` | Device: Secure Enclave ECDH key (iOS) or Keystore HMAC key (Android). Auth Core: `credentials.offline_secret_encrypted`, AES-256-GCM under `DEVICE_SECRET_ENCRYPTION_KEY` | Produces 8-digit offline codes |
| Push key `K` (push mode `NEXUS`) | Device: iOS keychain item readable after first unlock (not the Secure Enclave), Android Keystore AES-GCM and HMAC keys. Auth Core: `push_registrations.push_key_encrypted` under `DEVICE_SECRET_ENCRYPTION_KEY` | Opens the device's push messages; authenticates delivery receipts |
| Push message content | The bank backend, Auth Core memory while sealing, the phone. Stored and transported only as AES-256-GCM envelopes | Transaction notifications: amounts, counterparties, card spending |
| APNs auth key, FCM service account | `APNS_PRIVATE_KEY_PEM`, `FCM_SERVICE_ACCOUNT_JSON` from the secrets manager | Sending notifications to the bank's app |
| HSM evidence key | Bank HSM, selected by `PKCS11_TOKEN_LABEL`, `PKCS11_EVIDENCE_KEY_LABEL` and optionally `PKCS11_EVIDENCE_KEY_ID`; sensitive, not extractable | Seals evidence records, including enrolment and recovery records |
| Evidence records | `evidence_records`, one numbered chain per NEXUS ID | Proof of what the customer confirmed, with which key, enrolled how |
| Evidence chain heads | Each bank's own systems | The bank's independent reference for detecting removed or replaced records |
| Bank client secret and certificate fingerprints | scrypt hash and `bank_clients.mtls_cert_sha256` | Bank API access requires both the secret and a registered client certificate |
| Bank OAuth access tokens | Redis, under the SHA-256 of the token, TTL `OAUTH_TOKEN_TTL_SECONDS` | Full bank API access for one bank client, over its registered certificates |
| `BOOTSTRAP` tokens | Redis, under the SHA-256 of the token: single use, 300 s, optionally carrying a replacement authorization | Enrolment and device replacement |
| Recovery access tokens | SHA-256 hash in `recovery_sessions`, 600 s | Completing a recovery |
| Recovery key (protocol 2) | Public key and the private key wrapped under a phrase-derived key in `nexus_identities`; public key sealed in a `RECOVERY_CONFIGURED` record | Proves knowledge of the phrase at recovery |
| Admin passwords and TOTP secrets | scrypt hashes; TOTP secrets AES-256-GCM under `ADMIN_SECRET_ENCRYPTION_KEY` | Operator console login |
| Webhook secrets | AES-256-GCM under `WEBHOOK_SECRET_ENCRYPTION_KEY`, bound to the client ID | Authenticity of webhooks to the bank |
| Admin sessions | Redis, 30 minutes idle, 8 hours at most, ended by a password or TOTP reset | Operator console access |
| Audit records | `audit_logs`, append-only | Who did what, from where, for which bank |
| Personal data | `bank_customer_ref`, beneficiary values (names, account numbers) in `authorization_requests` and in the signed bytes kept in evidence; source IP and user agent in `authorization_attempts` and `audit_logs` | Customer and payee privacy |

Raw audio and video are not stored by NEXUS-SIGN; only the provider reference and the SHA-256 of the provider assertion are ([adaptive verification](../architecture/adaptive-verification.md)). Admin passwords and bank client secrets are stored as scrypt hashes; bank tokens, mobile tokens and admin sessions only as SHA-256 digests. The PKCS#11 PIN, the master keys and the attestation and push provider credentials are kept in the bank's secrets manager, never in source control or images.

## Trust boundaries

| Boundary | Between | Control at the boundary |
|---|---|---|
| Bank backend to Auth Core | Bank systems and the bank API | OAuth 2.0 client credentials; gateway mTLS with `REQUIRE_MTLS_HEADER` and `TRUSTED_PROXY_IPS`; tokens issued and accepted only with a client certificate fingerprint registered for the client (`src/middleware/mtlsGateway.ts`, `src/middleware/auth.ts`, `src/routes/oauth.ts`) |
| Gateway to Auth Core | The bank's gateway and Auth Core | Auth Core trusts `x-client-cert-verified` and `x-client-cert-sha256` only from `TRUSTED_PROXY_IPS`; the gateway must overwrite both on every request |
| Device to Auth Core | The customer's phone and the device routes | Device-signed requests; a `BOOTSTRAP` token for enrolment and a recovery session access token for recovery completion; the explicit route allow-list in `mtlsGateway.ts` exempts only these routes from gateway mTLS ([below](#gateway-mtls-trust-model)) |
| Auth Core to HSM | Auth Core and the PKCS#11 module | `HSM_ADAPTER=pkcs11`, PIN from the secrets manager, token and key selected by label and required to be unique, key attributes checked, startup and readiness self-test, per-operation deadline |
| Auth Core to PostgreSQL | Auth Core and its database | `DATABASE_SSL`; Auth Core connects as `nexus_app`, which owns no table and cannot disable triggers (`scripts/db/roles.sql`) |
| Auth Core to Redis | Auth Core and Redis | `REDIS_TLS_REQUIRED`, `rediss://`; deployment without failover to a replica that may lack recent writes |
| Database contents to Auth Core decisions | Rows in PostgreSQL and the keys Auth Core uses | Credential keys and recovery keys are used only if they match their HSM-sealed records (`src/services/credentialIntegrity.ts`) |
| Auth Core to attestation services | Auth Core, Apple App Attest root, Google Play Integrity decode API, Google key attestation roots | Pinned `APPLE_APP_ATTEST_ROOT_CA_PEM`; Google roots embedded in `src/crypto/androidAttestationRoots.ts`; status list from `ANDROID_ATTESTATION_STATUS_FILE`; `GOOGLE_SERVICE_ACCOUNT_JSON` from the secrets manager |
| Auth Core to bank webhook receivers | Outbound HTTPS | `WEBHOOK_ALLOWED_HOSTS`, `WEBHOOK_REQUIRE_HTTPS`, address checks, network egress rules (the DNS checks in the application are defence in depth); HMAC signature with timestamp, event ID for deduplication, no redirects; events written to an outbox in the transaction of the state change |
| Auth Core to APNs and FCM | Outbound HTTPS to Apple and Google (push mode `NEXUS`) | Only sealed envelopes and a generic alert text leave Auth Core; provider credentials from the secrets manager; egress limited to the provider hosts |
| Push receipt from the device | The phone (also the iOS notification service extension) and `POST /v1/push-receipts/{id}` | HMAC under the push key; exempt from gateway mTLS like the other device routes |
| Admin console | Operators and `/admin` | Gateway mTLS, password and TOTP, bank scope per account, four-eyes approval for revocation and reactivation; accounts provisioned only with the `createAdminUser` CLI |
| Host app to SDK | The bank's app process and the SDK | Confirmation text and biometric prompt built only from the signed bytes |

Auth Core is reachable only from the gateway or the private network; the gateway terminates external TLS and client mTLS.

### Gateway mTLS trust model

With `REQUIRE_MTLS_HEADER=true`, a request to a non-device route is accepted only when it arrives from an address in `TRUSTED_PROXY_IPS` (IPv4-mapped IPv6 forms compare as IPv4), carries `x-client-cert-verified: SUCCESS` (`MTLS_VERIFIED_HEADER`) and carries the SHA-256 fingerprint of the verified client certificate in `x-client-cert-sha256` (`MTLS_CERT_SHA256_HEADER`). `POST /oauth/token` issues a token only when the fingerprint is registered for the client, and every bank API call checks it again against the client of the presented token (401 and `bank_certificate_mismatch` otherwise), so a correct client secret alone is not enough.

The gateway must set or overwrite both headers on every request. Auth Core cannot tell a passed-through header from one the gateway set; if the gateway forwards a caller's `x-client-cert-sha256`, the binding is checked against a value the caller chose.

The routes the SDK calls directly are exempt, because a customer's phone does not hold the bank's client certificate: the device routes under `/v1/mobile/` (`bootstrap`, `recovery/setup`, `authorizations/{id}` and its verification and signature routes, `push-registration`, `push-messages/{id}`), `POST /v1/push-receipts/{id}` and `POST /v1/recovery/sessions/{id}/complete`. `/v1/mobile/sessions`, which the bank backend calls, is not exempt.

## Adversaries

| Adversary | Assumed capabilities | What the design still denies them |
|---|---|---|
| Malware on the phone | Runs as another app; can draw over the screen, read notifications and deep links, call the bank app's exported components | Use of the hardware keys outside the bank app; a signature or offline code without a biometric match for the signing or offline key. Malware that controls the bank app process or the operating system is outside what the SDK can defend against. |
| Network attacker | Reads, drops, replays and modifies traffic between the phone and the gateway, and between Auth Core and webhook receivers | Changing signed terms; replaying device requests or signatures; downgrading the SDK to plain HTTP |
| Holder of a stolen bank client secret | Knows `client_secret` but not the bank's client certificate | Obtaining or using a token (certificate binding, with a correctly configured gateway) |
| Malicious or compromised bank backend operator | Holds a bank client's OAuth credentials and mTLS certificate | Producing a customer signature, reading other banks' data. They can issue replacement tokens and open recovery sessions for that bank's customers, which is audited and visible to the bank (`credential.replaced`, `identity.recovered`), and can report audio or video results for that bank's sessions (NXS-019) |
| Writer to the database through the application role | Can `INSERT` and `UPDATE` operational rows as `nexus_app`, and `DELETE` push registrations | Changing or deleting evidence and audit records; deleting identities, credentials, authorizations, recovery sessions or admin approvals; disabling triggers; changing a credential's keys or an authorization's bound transaction; having a substituted credential key or recovery key accepted (refused at runtime and audited as `integrity_violation`) |
| Database superuser, provider admin role, members of `nexus_owner` | Can disable triggers and rewrite any row | Changes to evidence going undetected by a bank that holds the chain head and verifies with independently obtained public keys. Not denied: changes to unsealed operational data (identity status, bank clients, admin accounts) and their effects until detected |
| Insider with HSM access | Can sign arbitrary data with the evidence key | Producing a customer signature over terms the customer did not sign with an enrolled key. Combined with database write access, they can seal a forged enrolment record for a key they control; only the bank's chain heads and WORM copies remain independent |
| Admin console operator | Valid admin account | Acting on another bank's identities (bank scope); revoking or reactivating an identity alone (four-eyes). Not denied: suspending an identity, reading the bank's audit records |
| Compromised component between Auth Core and the device | A proxy, gateway or app backend relay that rewrites responses and requests | Making the device display or sign anything other than the server-issued canonical bytes; moving a device-signed request to another path or body |

## Residual risks

Open findings and limits of the current design. Items marked "open" are known and not fixed in 2.0.0-rc.2.

- **Audio and video verification results (NXS-019, FI-002; addressed in 2.0.0).** A result advances a plan only as a provider result token that Auth Core verifies against a provider key registered by the Auth Core operator, bound to the bank, session, authorization, transaction terms, device credential and session nonce, fresh and single-use ([verification result v1](../protocol/verification-result-v1.md)), or as the decision of an authenticated bank operator in the admin console. What remains outside Auth Core: how the provider or operator reached the result (identity, liveness, synthetic media).
- **Redis replication can bring back consumed state (NXS-021, open).** If Redis fails over to an asynchronous replica that missed recent writes, or is restored from a snapshot, used device request nonces and consumed BOOTSTRAP tokens (including replacement tokens) can be accepted again. This is an operational requirement on the Redis deployment ([deployment](../operations/deployment.md#redis)); Auth Core does not enforce it.
- **No App Attest assertions per operation and no periodic Play Integrity (NXS-025, open).** Attestation is checked at enrolment and recovery only. A credential stays usable after the device's integrity changes.
- **TLS public-key pinning in the SDKs is optional (NXS-028, mitigated when configured).** Since 2.0.0 both SDKs accept `certificatePins` (SPKI SHA-256, at least two). Without them the SDKs rely on the platform's certificate validation. Refusal of a non-pinned chain still needs a device test.
- **Gradle distribution checksum and dependency verification metadata missing (NXS-039, open).** They need access to services.gradle.org and Maven repositories. The wrapper JAR is validated in CI by `gradle/actions/setup-gradle`.
- **Base images not pinned by digest (NXS-040, open).** `node:22-alpine` is referenced by tag; pinning needs registry access.
- **No committed `package-lock.json`.** CI and the Dockerfile require one and fail without it; it must be generated with registry access and reviewed before a release can be built.
- **Database superuser and owner.** `nexus_app` cannot disable the triggers, but a superuser, the provider's admin role or a member of `nexus_owner` can, and can rewrite any row. Changes to evidence are detectable against the bank's chain heads and independently held public keys; changes to unsealed data (identity status, bank clients, admin accounts, recovery session counters) are not detectable by Auth Core. Log DDL with `pgaudit` or the provider's audit log.
- **The application role writes operational tables.** Whoever holds `nexus_app` credentials can change identity status, bank client records (including registered certificate fingerprints and status) and admin accounts (role, scope, status). Credential keys, recovery keys, evidence and audit records are protected as described above; these tables are not.
- **HSM key plus database write.** Someone who can sign with the evidence key and write to the database can seal a forged enrolment record that the runtime check and the offline verifier accept. Chain heads held by the banks and WORM copies are the remaining independent reference ([incident response](../operations/incident-response.md#hsm-evidence-key-compromised)).
- **Baseline enrolment records.** Credentials enrolled before 2.0 were sealed by `sealCredentialBaseline` with the keys the database held at the upgrade; the record cannot prove how those keys got there, and Android credentials from before 2.0 have no key attestation.
- **Chain truncation without a stored head.** The verifier detects removed trailing records only with `--expect-head`. A bank that does not store heads cannot detect them.
- **Android status list freshness.** Auth Core does not check the age of `ANDROID_ATTESTATION_STATUS_FILE`; a stale list accepts recently revoked attestation keys. Existing credentials are not re-checked when a key is revoked later.
- **Protocol 1 customers.** Identities still on recovery protocol 1 cannot recover with their phrase until they set up a new one; the bank uses device replacement for a customer who has lost the device.
- **Single-person suspension.** Suspension is deliberately one-person; an admin can suspend any identity in scope, which blocks the customer until two admins reactivate it.
- **The bank's own decisions.** A bank backend operator with valid credentials and certificate can create authorizations, issue replacement tokens and open recovery sessions for that bank's customers. The customer signature, the audit records and the webhooks record what happened.
- **Offline codes** are verifiable only by Auth Core, which holds the shared key, not by third parties. Banks that need non-repudiation for a payment type require online confirmation for it.
- **Homoglyphs.** The display rule covers invisible and layout characters only. Visually similar characters from other scripts are accepted in beneficiary values.
- **Redis read access.** Tokens are stored under their SHA-256, so a copy of Redis does not reveal them; someone who can write to Redis can create tokens. Redis access belongs to the Auth Core service only.
- **Push.** Someone holding the bank's APNs auth key or FCM service account can send notifications with their own visible text to the bank's app; they cannot produce a message that opens as a NEXUS-SIGN push. On iOS the push key is a keychain item, not a Secure Enclave key. A push envelope replayed through the provider shows the original message again.
- **SDK verification.** The Swift and Kotlin code of 2.0.0-rc.2, including the device-side recovery protocol, Android key attestation, the iOS biometric change detection and the removal of bearer tokens from both SDKs, has not been built with the platform toolchains or tested on devices; the Kotlin sources were only compiled against API stubs ([release](../operations/release.md)).
