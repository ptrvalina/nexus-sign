## 3. Путь до банковского исполнения

**Шаги 1–10 прослежены по коду.**
- Создание операции → офлайн-код → подпись устройства → сохранение подписи и доказательств → проверка подписи → печать HSM → привязка → `VERIFIED` → `bank-commit-request` → вебхуки и `bank-commit-result`.
- `VERIFIED` пишут только `finalizeVerified` (онлайн-подпись, код v1, подпись v2) и прямая запись в базу.
- Других путей к исполнению нет:
  - административные маршруты состояние только читают (отзыв устройства может лишь отменить ожидающие операции);
  - входящих вебхуков в Auth Core нет;
  - фоновые задачи переводят операции только в `EXPIRED` и `OFFLINE_UNSIGNED`;
  - демо-банк ничего не исполняет.
- `OFFLINE_PROVISIONAL` и `OFFLINE_UNSIGNED` исполнить нельзя: `bank-commit-request` требует `VERIFIED` и действительные доказательства.

**Исправлено в этой фазе**
1. Запись с настоящей печатью, вставленная рядом с цепочкой доказательств, а не в её конец, раньше проходила проверку при исполнении. Теперь сверяются запечатанные `chainSequence` и `previousEvidenceHash` с сохранённой строкой и предыдущей записью (D-036).
2. `confirmed: true` раньше выставлялось по одному лишь полю состояния, поэтому запись в базу давала `confirmed: true`. Теперь `confirmed` истинно, только если запечатанные доказательства проходят ту же проверку в момент запроса; иначе в ответе есть `evidenceProblem`. Это значение, вычисленное Auth Core, а не самостоятельный криптографический факт для банка.

**Атомарность.**
- Проверка доказательств и переход `PENDING → COMMIT_REQUESTED` выполняются в одной транзакции под блокировкой строки — внутри Auth Core между ними ничего не может вклиниться.
- Тест: 20 параллельных запросов с одной ссылкой дают одну зафиксированную заявку; из 10 запросов с разными ссылками принимается ровно один.
- После ответа 202 исполнение — ответственность банка: один раз на `bankTransactionReference`, затем отчёт о результате. Деньги переводит банк, не Auth Core.

## 4. Тест «действительная печать HSM + неверная подпись устройства»

**Стенд.** Auth Core работает на SoftHSM (`HSM_ADAPTER=pkcs11`). Тест сам ставит печать настоящим ключом доказательств из токена — `C_Sign`, `CKM_ECDSA_SHA256` в отдельном процессе, — то есть делает то же, что мог бы атакующий с доступом к HSM. Запись вставляется ровно туда, куда её дописал бы Auth Core, а строка операции переводится в `VERIFIED` записью в базу. Результаты криптографических проверок не мокируются.

**Контроль.** Правильно собранная запись с такой же печатью принимается: верификатор её одобряет, `confirmed: true`, запрос на исполнение получает 202. Значит, печати настоящие, и отказы ниже вызваны именно проверяемыми условиями.

| Подделка (печать действительна) | Исполнение | Верификатор |
|---|---|---|
| Подпись устройства чужим ключом | 409 `EVIDENCE_INVALID`: «device signature … does not verify» | отклоняет |
| Корректная подпись над изменёнными условиями | 409: «does not carry the stored terms» | — |
| Настоящая запись другой операции | 409: «names another authorization» | — |
| Ключ и подпись другого устройства | 409: «another device key» | — |
| Устаревшая или неизвестная ссылка на регистрацию | 409: «another enrolment» | — |
| Нет обязательного поля | 409 | — |
| Метод «только код» на развёртывании v2 | 409: «code-only … not accepted» | — |
| Неизвестный ключ печати | 409: «unknown evidence key» | — |
| Запись вне своей позиции в цепочке | 409: «does not link to its predecessor» | проверка цепочки видит разрыв |

В каждом случае:
- создаётся событие `integrity_violation`;
- состояние банковской транзакции остаётся `PENDING` (частичного исполнения нет);
- `GET` возвращает `confirmed: false` и причину.

Кроме того:
- запечатанная запись не меняет состояние операции `PENDING_USER`;
- запись подтверждённой операции, изменённая после подтверждения (в обход триггера), не исполняется;
- устройство, отозванное после подтверждения, даёт `CREDENTIAL_NOT_ACTIVE`.

Набор: 13/13.

## 5. Остаточные риски по сценариям

Полная таблица — в `docs/security/offline-confirmation-threat-model.md` («Phase 10»). Кратко:

| Сценарий | Что остаётся возможным |
|---|---|
| Только база | отказ в обслуживании; `state: VERIFIED` при `confirmed: false` |
| База и мастер-ключи | только предварительные состояния |
| Полный контроль над Auth Core | поддельная регистрация устройства и подписанные ею одобрения; блокировка и задержка. Обнаруживается только вне Auth Core: верификатор банка с ключами, полученными отдельно, `--reject-offline-code`, `--heads`, сверка регистраций (не реализована) |
| Компрометация устройства | всё, что разрешает ключ устройства (FI-007) |
| Злоупотребление оператора | пропуск клиента через нечестный звонок: решение оператора закрывает шаг плана, но подпись устройства всё равно нужна |
| Компрометация регистрации | через базу — предотвращено; через Auth Core — см. выше |
| Повторное исполнение | двойное исполнение на стороне банка, если он игнорирует результат запроса на исполнение |
| Отказ HSM | недоступность подтверждений |
| Компрометация HSM | полностью согласованные записи — только вместе с контролируемым Auth Core |
| Подмена данных до подписи | похожие на вид имена получателей подписываются как есть (FI-034); клиент может не прочитать экран |
| Канал доставки | задержка и потеря; предварительные подтверждения заканчиваются `OFFLINE_UNSIGNED` |

Компрометация Auth Core не устранена: это доверенный компонент с широкими полномочиями.

**Векторы протокола.** Новые — валидные:
- имя получателя с кириллическими буквами, похожими на латинские: подписывается и показывается как есть;

Новые — невалидные:
- сумма из 31 цифры; валюта с цифрой или из 4 букв;

- идентификатор операции не в формате UUID; идентификатор устройства в верхнем регистре; NEXUS ID из 8 цифр.

**Найдено:** разбор подписываемых байтов на Android, iOS и в sandbox не проверял форматы идентификаторов и nonce, хотя протокол этого требует (D-037). Исправлено. Если убрать новые проверки, тесты на Android и в sandbox падают — это проверено. Код iOS не компилировался.

Истёкший срок, изменённый nonce, неизвестный ключ печати и подпись чужим ключом проверяются на сервере интеграционными тестами (DS 7/8, FH, DS 4).

**Мутации.** Отдельный прогон на коде `8635a04` (тот же код, что `b7e6cb6`). Наборы: `offline-deferred-signature`, `offline-enforcement`, `evidence-forgery-hsm` (с SoftHSM). Прогон, в котором какой-либо тест пропущен, считается недействительным.

## 7. FI-005

**Проверено на SoftHSM** (локальная эмуляция интерфейса, не HSM поставщика):
- KEK создаётся внутри HSM, импортированный KEK отклоняется; извлекаемый или нечувствительный KEK отклоняется;
- без HSM запуск не происходит; отката к открытым ключам нет;
- смена KEK; ротация с перезапуском до, после и **посреди работы инструмента** (новый тест: убит SIGKILL, незавершённая порция откатывается целиком, все секреты целы, повторный запуск завершает ротацию);
- хранимый формат расшифровывается внутри HSM; секретов в логах нет.

**Требует HSM поставщика (BLOCKED):**
- механизмы и политика IV для GCM;
- атрибуты ключей;
- разделение ролей;
- резервное копирование и восстановление (только описаны);
- ротация на мастер-ключ, созданный в HSM (не реализована);
- задержки.

**Мастер-ключи в памяти процесса — не закрыто.**

## 8. FI-009 и WebRTC

- Lockfile отсутствует и не создавался.
- Реестры недоступны: npm и PyPI — DNS, Maven и Google Maven — 403; GitHub не привязан; Docker-демона нет.
- **Закреплено:**
  - Gradle wrapper jar лежит в репозитории (SHA-256 вычислен, с официальным списком не сверен);
  - зависимости CI-actions закреплены по коммитам.
- **Не закреплено:**
  - зависимости npm;
  - дистрибутив Gradle (`distributionSha256Sum`) и зависимости Gradle (нет `verification-metadata.xml`);
  - `Package.resolved`;
  - базовые образы Docker (только теги);
  - бинарники WebRTC.
- **Локально выполнено:** перечень лицензий собранного для тестов дерева зависимостей (132 пакета: MIT 121, Apache-2.0 5, ISC 5, BSD-3-Clause 1) — **не авторитетный**, дерево собрано не из lockfile; поиск секретов по шаблонам.

- **WebRTC:** версии не менялись; артефакты не скачаны; контрольные суммы, исходные ревизии, лицензии внутри бинарников и уязвимости не установлены. TPM-1…TPM-7 открыты.
