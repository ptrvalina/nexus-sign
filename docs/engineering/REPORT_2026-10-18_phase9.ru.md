## 3. FI-004 — что сделано

**Решение владельца закреплено (D-033).**
- `OFFLINE_PROVISIONAL` — не разрешение на исполнение.
- `VERIFIED` возможен только с действительной подписью зарегистрированного устройства над точными каноническими байтами.
- Режим «только код» в продакшене запрещён.
- Отложенная подпись остаётся режимом по умолчанию.
- Обходов, при которых интеграция могла бы считать `OFFLINE_PROVISIONAL` равным `VERIFIED`, нет.

Это техническое правило авторизации, а не вывод о юридической силе подписи.

**Прослежены все пути к исполнению.**
- Состояние `VERIFIED` пишут только три функции:
  - `finalizeVerified` — для онлайн-подписи, кода v1 и подписи v2;
  - переход по триггеру БД — при прямой записи в базу;
  - `PROVISIONAL` и `UNSIGNED` пишут только `acceptOfflineCode` и обработчик истечения.
- Других путей к `VERIFIED` нет. Административные маршруты состояние читают; через отзыв устройства они могут только отменить ожидающие операции. Входящих вебхуков в Auth Core нет (`evidence.appended` и `authorization.verified` — исходящие).
- Демо-банк платежи не исполняет, только показывает их.
- Sandbox — отдельный симулятор протокола v1, данные Auth Core он не трогает.

**Найдено и исправлено.**
- Запрос банка на исполнение (`bank-commit-request`) верил только полю `state`.
- Триггер БД разрешает переход `PENDING_USER → VERIFIED` с любым непустым значением подписи. Поэтому тот, у кого есть запись в базу от имени приложения, мог сделать строку, которую принимал этот запрос. Проверено так: мутация M14 возвращает прежнее поведение — и тест «VERIFIED, записанный в базу напрямую» с ней падает, потому что запрос принимается. На текущем коде тест проходит.
- Теперь перед исполнением проверяется запечатанная запись доказательств (D-034):
  - печать HSM;
  - привязка к операции, устройству, личности и сохранённым условиям;
  - совпадение способа подтверждения;
  - подпись устройства ключом, запечатанным при регистрации;
  - в режиме v2 запись «только код» (`OFFLINE_CODE`) не принимается.
- Иначе — 409 `EVIDENCE_INVALID` и событие `integrity_violation`.

**Однозначность статусов.**
- `GET /v1/authorizations/{id}` и события `authorization.verified` / `offline_provisional` / `offline_unsigned` содержат `confirmed`: `true` только для `VERIFIED`.
- Демо-банк показывает «подтверждён» только при `VERIFIED` и `confirmed: true`. Неизвестное состояние или ошибка ответа подтверждением не считаются (тест).
- `OFFLINE_CONFIRMATION_MODE=immediate` вне продакшена теперь требует `ALLOW_INSECURE_DEVELOPMENT=true`. Изменение конфигурации не включит старый режим неявно.

**Проверка «то же устройство» на уровне сервиса (D-035).** Тест вызывает скомпилированную функцию `submitDeferredSignature` в отдельном процессе, минуя HTTP-маршруты:
- с чужим устройством функция выбрасывает `ForbiddenError`, состояние не меняется;
- тот же вызов с правильным устройством завершается `VERIFIED` — значит, отказ вызван именно проверкой устройства.

Защита есть на обоих уровнях.

## 6. FI-005 и ограничения SoftHSM

- **Проверено локально** (SoftHSM — локальная эмуляция интерфейса PKCS#11, не HSM поставщика):
  - продакшен требует `MASTER_KEY_SOURCE=hsm` (unit);
  - нет отката к открытым ключам: в режиме `hsm` ключи берутся только из расшифрованных при старте, открытые значения рядом с `hsm` останавливают запуск;
  - импортированный KEK отклоняется; извлекаемый или нечувствительный KEK отклоняется;
  - ошибка HSM останавливает запуск;
  - смена KEK и ротация переживают перезапуск;
  - в логах нет ключевого материала.
- **Не тестировалось:** прерывание инструмента ротации посреди работы. Резервное копирование и восстановление только описаны.
- **Ключи в памяти процесса** — **не закрыто.** Новый тест `hsm-in-place-decryption` (SoftHSM) показывает:
  1. Хранимый формат `k1` расшифровывается в HSM через `C_Decrypt` + `CKM_AES_GCM` с теми же связанными данными, неверные связанные данные HSM отклоняет. Менять формат не нужно.
  2. Перенести существующие мастер-ключи в HSM без расшифровки в процессе на SoftHSM нельзя: `C_UnwrapKey` с `CKM_AES_GCM` и путь RFC 5649 дают `CKR_MECHANISM_INVALID`. Рабочий путь — новый мастер-ключ, созданный в HSM, и ротация всех секретов на него.
  3. Около 20 мкс на секрет на SoftHSM; сетевой HSM добавит свою задержку.

  Схема не менялась: нужна проверка на HSM поставщика (механизмы, политика IV в режиме FIPS, задержки, отказоустойчивость). От атакующего, управляющего процессом, это не защищает.
- **HSM поставщика: BLOCKED.**

## 10. Остаточные риски

1. **Обход Auth Core банком.** Процесс банка может исполнить платёж, не вызвав `bank-commit-request` и не проверив `confirmed`. Это правило интеграции, его не обеспечить на стороне Auth Core.

3. **Скомпрометированный телефон.** FI-007 открыт.
4. **Мастер-ключи в памяти процесса.**
5. **Старые SDK.** На v2 они не могут подтверждать офлайн.
6. **Нативные SDK не проверены.** Android проверен только на JVM с заглушками, iOS не компилировался, устройств не было.
7. **Входные данные сборки не закреплены** (R-21), lockfile нет.
8. **Происхождение и лицензии WebRTC не подтверждены.**
