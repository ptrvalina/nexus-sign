## A. Что изменено

**Auth Core**
- Миграция `022_offline_deferred_signature.sql` (аддитивная): состояния `OFFLINE_PROVISIONAL` и `OFFLINE_UNSIGNED`, способ подтверждения `OFFLINE_SIGNED`, поля принятого кода и срока подписи, таблица `offline_deferred_signatures` (только добавление), новый триггер переходов. Отдельно: `policy_reference` и `policy_version` теперь неизменяемы (D-030; раньше их изменение ловила только проверка хеша при подтверждении).
- `authorizationConfirmation.ts`: принятие кода в v2 (`acceptOfflineCode`), приём подписи (`submitDeferredSignature`), перевод в `OFFLINE_UNSIGNED` (`expireUnsignedOfflineConfirmations`, в воркере истечения). Суточный лимит офлайн-подтверждений теперь проверяется в той же транзакции, что фиксирует принятие кода, под блокировкой на устройство.
- Новый маршрут `POST /v1/mobile/authorizations/{id}/deferred-signature`; OpenAPI (44 маршрута); ответы 202, 409 `NOT_AWAITING_SIGNATURE`, 422 `INVALID_DEFERRED_SIGNATURE`.
- Конфигурация: `OFFLINE_CONFIRMATION_MODE` (`deferred_signature` по умолчанию, в продакшене обязателен), `OFFLINE_SIGNATURE_DEADLINE_HOURS` (72).
- Проверка доказательств: записи `OFFLINE_SIGNED` проверяются как обычная подпись устройства; ключ `--reject-offline-code` отклоняет записи «только код».
- FI-005: KEK должен быть создан в HSM (`CKA_LOCAL`, `CKA_NEVER_EXTRACTABLE`) — импортированный ключ теперь отклоняется (D-031); копия K стирается сразу после сравнения кода.

**SDK**
- Android: префикс `NXS2.`, `requiresDeviceSignature`; в `confirmOffline` сначала подпись ключом подписи и запись в очередь, потом код; `submitPendingOfflineSignatures()`; очередь `OfflineSignatureQueue` (SharedPreferences, `commit()`).
- iOS: то же для `NEXUSSign` — одна оценка `LAContext` на оба ключа. **Не компилировалось.**

**Документация**: спецификация протокола v2, ADR 0018 (и поправка к ADR 0003), новая модель угроз, D-029…D-032, руководство банка, конфигурация, обновление до 2.0, состояния, формат доказательств, совместимость, чек-лист устройств (F3–F8), происхождение WebRTC, проверка FI-005, риски.

## B. FI-004 — отложенная подпись устройства

**Модель угроз до и после** (полностью — `docs/security/offline-confirmation-threat-model.md`):

| Кто скомпрометирован | v1 (только код) | v2 |
|---|---|---|
| Только база данных | нет | нет (вставленная строка подписи перепроверяется; таблица только на добавление) |
| База + мастер-ключ (`env`) | **да** | только `OFFLINE_PROVISIONAL`, затем `OFFLINE_UNSIGNED` |
| База + конфигурация + доступ к HSM | **да** | только `OFFLINE_PROVISIONAL` |
| Работающий Auth Core | **да** | не может создать подпись устройства; **может**: блокировать и задерживать, подделать запись v1 `OFFLINE_CODE` (ловится `--reject-offline-code`), подделать запись о регистрации устройства (ловится только сверкой регистраций у банка), показать на экране банка другой QR (телефон покажет эти условия) |
| Устройство клиента | да | да — ключ устройства и есть якорь доверия |
| Учётная запись администратора | нет | нет (может отозвать устройство — это отказ в обслуживании) |

**Изменения протокола**: подписываются те же канонические байты v1 тем же ключом и алгоритмом, что онлайн; новый формат не вводился. QR `NXS2.` означает «подписать и выдать код». Старые SDK такой QR отклоняют — они не оставят платёж навсегда «предварительным». Состояния и переходы закреплены триггером.

**Что подпись доказывает**: зарегистрированный ключ этого устройства подписал именно эти условия (сумма, валюта, получатель, ссылка, политика, срок, nonce) после локальной биометрии.

**Что не доказывает**: время подписи (часы телефона ничего не доказывают); что клиент прочитал и понял условия; что операция была ещё актуальна (офлайн телефон не знает об отмене, отзыве, повторе); что телефон не был скомпрометирован; что платёж можно исполнить. **Источник истины — банк.**

**Тесты** (`offline-deferred-signature.test.mjs`, 19/19): код, потом подпись; подпись, потом код; подпись с изменённой суммой, другим получателем, от другой операции; чужой ключ; запрос от другого устройства (403); отзыв устройства во время ожидания; неизвестный формат; истёкшая операция; уже подтверждённая операция; срок подписи вышел (до и после работы фонового обработчика); повторная доставка; 20 параллельных отправок подписи и 20 параллельных кодов; код и подпись одновременно; процесс убит (SIGKILL), пока загрузка ждёт блокировку строки, затем перезапуск и повтор; подмена записи доказательств; изменение условий и версии политики; строка подписи, вставленная в базу напрямую; инсайдер с K; суточный лимит, в том числе 6 параллельных кодов; режим v1; запрет v1 в продакшене; `--reject-offline-code`.

**Мутационная проверка** (каждая мутация снимает одну защиту; набор должен упасть):

| Мутация | Результат |
|---|---|
| Код без подписи даёт `VERIFIED` | обнаружена (17 тестов) |
| Сохранённая подпись не перепроверяется | обнаружена |
| Неверная подпись принимается | обнаружена |
| Подпись от любого устройства | **не обнаружена**: на уровне API её уже отсекает проверка области запроса (чужая личность) и правило «одно активное устройство на личность»; проверка в сервисе — дополнительный рубеж |
| Срок подписи не проверяется | обнаружена (после добавления теста 8b) |
| Нет блокировки строки | обнаружена |
| Поля офлайн-кода изменяемы | обнаружена |
| Суточный лимит только до сравнения кода | обнаружена |
| Обработчик не учитывает отзыв | обнаружена |
| v1 разрешён в продакшене | обнаружена |
| Проверка доказательств не проверяет ECDSA для `OFFLINE_SIGNED` | сначала **не обнаружена** (тест ловил изменение хеша, а не подписи); тест 13 усилен, теперь обнаружена |
| Таблица подписей изменяема | обнаружена |
| Подпись принимается в режиме v1 | обнаружена |

**Остаточные риски**: банк может исполнить платёж на `PROVISIONAL`; контролируемый Auth Core может подделать записи v1 и регистрации; телефон с вредоносным ПО подпишет что угодно (FI-007); старые приложения не смогут подтверждать офлайн; откат базы даёт ложный `OFFLINE_UNSIGNED` (но никогда ложный `VERIFIED`); на Android два запроса биометрии. Лимиты суммы и количества остаются и ограничивают только первый случай — устранением они не являются.

**Совместимость**: изменение аддитивно для данных, но меняет поведение по умолчанию. Банк, который действует только на `VERIFIED`, защищён без изменений. Банк, который считает успехом всё, кроме `FAILED`, должен обработать `PROVISIONAL`. Старые верификаторы отклоняют `OFFLINE_SIGNED` — их нужно обновить первыми. Режим v1 (`immediate`) остаётся вне продакшена. Откат Auth Core на rc.2 при наличии строк `OFFLINE_PROVISIONAL` не поддерживается.

**Нужно решение владельца и банков** (D-029): разрешено ли банку исполнять платёж на `PROVISIONAL`. Auth Core его не подтверждает и отказывает в `bank-commit-request`; рекомендация документации — ждать `VERIFIED`.

**Статус FI-004: PARTIAL** — сервер реализован и проверен локально, SDK не собраны и не проверены на устройствах.

## C. FI-005 — HSM и мастер-ключи

- **Проверено на SoftHSM 2.7.0** (локальный тест, не PASS гейта): `master-key-hsm.test.mjs` 11/11 — работа только с обёрнутыми ключами; копии базы и конфигурации недостаточно; ротация и смена KEK; отказ при недоступном HSM, неверном PIN, неизвестном KEK, ключе другого назначения, KEK без права расшифровки, **импортированном KEK (новое)**; в логах нет ключевого материала.
- **Разбор кода** (своя проверка, не независимый аудит): AES-256-GCM, IV 96 бит (HSM XOR Node), тег 128 бит, связанные данные с именем ключа, проверка атрибутов, отказ при старте. Не тестировалось: прерывание инструмента ротации посреди работы.
- **Остаётся проверить на реальном HSM**: параметры GCM (`CK_GCM_PARAMS` v2.40 у поставщика), политика атрибутов, разделение ролей и разделов, резервное копирование, ключевая церемония. **BLOCKED**: HSM нет.
- **В памяти процесса остаются**: три мастер-ключа и все `_PREVIOUS` — всё время работы Auth Core и, пока работают, — утилиты. Расшифрованные секреты (секреты вебхуков, TOTP) — кратковременно, без явного стирания; K теперь стирается. Перенос мастер-ключей в HSM с расшифровкой на каждую операцию совместим с форматом хранения (D-032), но не реализован: его нужно проверять на HSM поставщика, а от атакующего, управляющего процессом, он не защищает.

**Статус FI-005: PARTIAL.**
