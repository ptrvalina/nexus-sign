# Recovery protocol 2

Recovery moves a customer's NEXUS ID to a new device when the old one is lost. The customer proves knowledge of a 12-word recovery phrase; the bank backend opens the recovery session after it has re-identified the customer through its own controls. The phrase never leaves the device.

In protocol 2 the phrase protects a P-256 recovery key. Auth Core stores the public half and the private half encrypted under a key derived from the phrase, and checks a signature by the recovery key. Nothing Auth Core stores is enough to complete a recovery. Protocol 1 stored a PBKDF2 verifier that was itself the HMAC key of the proof, so whoever could read it could recover the identity without the phrase; it was removed in 2.0.0-rc.2 ([protocol 1](#protocol-1)).

Implementations: `auth-core/src/services/recoveryService.ts` (server), `ios-sdk/Sources/NEXUSSign/RecoveryProtocol.swift`, `android-sdk/src/main/kotlin/com/nexis/nexussign/RecoveryProtocol.kt`, and `auth-core/scripts/lib/recovery.mjs` (device side in Node.js, used by the smoke test and the integration suites). Decision record: [ADR 0010](../adr/0010-recovery-protocol-v2.md).

## Parameters

| Parameter | Value | Where it is set |
|---|---|---|
| Phrase | 12 words, BIP-39 English word list, from 128 bits of random entropy plus a 4-bit checksum | Generated by the SDK (`SecRandomCopyBytes`, `SecureRandom`) |
| KDF | PBKDF2-HMAC-SHA256, 32-byte output | Fixed |
| Iterations | 210 000 | Auth Core (`ITERATIONS`); the SDKs accept 100 000 to 5 000 000 |
| Salt | 16 random bytes, fresh for every setup | Auth Core; the SDKs require at least 16 bytes |
| Recovery key | ECDSA P-256, generated in memory on the device | SDK |
| Wrapped key | 60 bytes: IV (12) ‖ encrypted scalar (32) ‖ GCM tag (16) | SDK |
| Session nonce | 32 random bytes | Auth Core |
| Setup parameters lifetime | 600 s, single use | Auth Core (Redis) |
| Recovery session lifetime | 600 s | Auth Core |
| Attempts per session | 5 | Auth Core |
| Failed proofs per identity | 10 in 24 hours | Auth Core |

The phrase is normalized before derivation: words are trimmed, lower-cased and split on whitespace, and joined with single spaces. The SDKs refuse a phrase whose words are not in the list or whose checksum is wrong before any derivation.

## Setup

Setup runs on the enrolled device, which signs the registration with its biometric signing key. A new setup replaces the previous recovery key.

### 1. Parameters

`GET /v1/mobile/recovery/setup` (device-signed request) returns:

```json
{ "protocol": 2, "kdf": "PBKDF2-HMAC-SHA256", "iterations": 210000, "keyLength": 32,
  "salt": "<16 random bytes, base64>", "nexusId": "123456789", "credentialId": "<the requesting credential>" }
```

Auth Core remembers the salt for this credential for 600 s (`recovery_setup:<credentialId>`). The SDKs refuse parameters outside the bounds above, and parameters naming another credential.

### 2. Key generation and wrapping

```text
phrase   = 12 words from 128 bits of entropy (BIP-39)
seed     = PBKDF2-HMAC-SHA256(P = UTF-8(normalized words joined by " "), S = salt, c = iterations, dkLen = 32)
wrapKey  = HKDF-SHA256(IKM = seed, salt = "NEXUS-SIGN/RECOVERY-WRAP/v2", info = UTF-8(nexusId), L = 32)
(d, Q)   = new random P-256 key pair
AAD      = UTF-8("NEXUS-SIGN/RECOVERY-KEY/v2" "\n" nexusId "\n" hex(SHA-256(SPKI(Q))))
wrapped  = IV (12 random bytes) || AES-256-GCM(wrapKey, IV, AAD, d as 32 bytes big-endian) || tag (16 bytes)
```

`SPKI(Q)` is the DER SubjectPublicKeyInfo of the recovery public key; `hex` is lowercase. The associated data binds the wrapped key to the identity and to its public key, so it cannot be opened under another NEXUS ID or presented with another public key.

The recovery key is not created in the Secure Enclave or the Keystore, because it has to be restorable on a different device. Its private half exists in app memory only while a phrase is set up or used; Android overwrites the seed, the wrapping key and the scalar after use.

### 3. Setup signing input

Signed with the device's biometric signing key (ECDSA P-256 / SHA-256, DER), after a biometric prompt:

```text
NEXUS-SIGN/RECOVERY-SETUP/v2
<nexusId>
<credentialId>
<salt, base64, exactly as received>
<hex SHA-256 of SPKI(Q)>
<hex SHA-256 of wrapped>
```

Lines are joined with `\n`, UTF-8, no trailing newline.

### 4. Registration

`POST /v1/mobile/recovery/setup`:

```json
{ "protocol": 2, "salt": "<base64>", "recoveryPublicKeyPem": "-----BEGIN PUBLIC KEY-----…",
  "wrappedRecoveryKey": "<60 bytes, base64>", "signature": "<DER, base64>" }
```

Auth Core checks, in this order:

1. The request is a device-signed request of an enrolled device whose keys match its sealed enrolment ([evidence format](evidence-format.md#runtime-integrity-check)); a `BOOTSTRAP` token is refused (403).
2. The body: `protocol` is `2`, field lengths are within bounds.
3. The credential's keys match its sealed enrolment again (`assertCredentialIntegrity`).
4. The salt is the one issued to this credential and not yet used. It is taken from Redis atomically (`GETDEL`), so it is consumed by this request even if a later check fails. Otherwise: 409 `RECOVERY_SETUP_EXPIRED`.
5. `recoveryPublicKeyPem` is a strict P-256 public key PEM.
6. `wrappedRecoveryKey` decodes to exactly 60 bytes (400 otherwise).
7. `signature` verifies over the setup signing input with the credential's signing public key. Otherwise: 400 and audit event `recovery_setup_rejected`.
8. In one transaction: the identity is `ACTIVE` (row locked) and the credential is still `ACTIVE`; the identity row is updated (protocol 2, public key, wrapped key, salt, iterations); a `RECOVERY_CONFIGURED` evidence record is sealed and the identity points at it (`recovery_evidence_id`); audit event `recovery_configured`; webhook `recovery.configured` (`nexusId`, `credentialId`, `configuredAt`).

The response is 204. Because the registration is signed by the biometric key, a request-signing key alone cannot replace the recovery key.

## Recovery

### 1. Session

After re-identifying the customer, the bank backend calls `POST /v1/recovery/sessions` with `{ "bankCustomerRef": "…" }` (bank token, gateway mTLS). Auth Core refuses the session when:

| Condition | Response |
|---|---|
| No `ACTIVE` identity for this reference and bank client | 404 |
| No recovery configured | 409 |
| Identity on protocol 1 | 409 `RECOVERY_PROTOCOL_RETIRED` |
| 10 or more failed proofs in sessions of this identity created in the last 24 hours | 409 `RECOVERY_LOCKED`, audit event `recovery_locked` |
| The stored configuration fails the [integrity check](#integrity-check) | 409 `RECOVERY_INTEGRITY`, audit event `integrity_violation` |

Otherwise it returns 201:

```json
{
  "sessionId": "<uuid>",
  "nexusId": "123456789",
  "nonce": "<32 random bytes, base64>",
  "accessToken": "rc_…",
  "parameters": { "protocol": 2, "kdf": "PBKDF2-HMAC-SHA256", "iterations": 210000, "keyLength": 32, "salt": "<base64>" },
  "recoveryPublicKeyPem": "-----BEGIN PUBLIC KEY-----…",
  "wrappedRecoveryKey": "<60 bytes, base64>",
  "expiresAt": "…"
}
```

The bank backend hands the session to its app. Auth Core stores only the SHA-256 of the access token. Audit event `recovery_started`.

#### Integrity check

Before a session is created, and again at completion, Auth Core checks the identity's stored protocol 2 configuration against its sealed `RECOVERY_CONFIGURED` record (`assertRecoveryKeyIntegrity` in `recoveryService.ts`):

- `recovery_evidence_id` is set and names an existing schema 3 record whose hash and HSM seal verify with the current or a retired evidence key;
- the record is a `RECOVERY_CONFIGURED` record of this NEXUS ID;
- its `recoveryPublicKeyPem` is the stored public key and its `wrappedRecoveryKeySha256` is the SHA-256 of the stored wrapped key;
- it is the identity's latest `RECOVERY_CONFIGURED` record (highest `chain_sequence`), so an earlier configuration the customer has replaced cannot be restored;
- at session creation only: the stored salt and iteration count are the sealed `kdfSaltB64` and `kdfIterations`, so the device receives exactly the parameters it registered.

A failure is answered 409 `RECOVERY_INTEGRITY` and written as audit event `integrity_violation`.

### 2. Opening the wrapped key

On the new device the SDK:

1. Normalizes the phrase and checks the words and checksum.
2. Checks that `sessionId` is a UUID and the parameters are within bounds (protocol 2, PBKDF2-HMAC-SHA256, 32-byte key, 100 000 to 5 000 000 iterations, salt of at least 16 bytes).
3. Derives `seed` and `wrapKey` as in setup, with the session's salt, iterations and `nexusId`, and opens `wrappedRecoveryKey` with AES-256-GCM and the associated data built from `recoveryPublicKeyPem`.

A wrong phrase fails the GCM tag on the device (`invalidRecoveryPhrase` / `InvalidRecoveryPhrase`). Nothing is sent to Auth Core and no server attempt is used. iOS also checks that the opened scalar yields the session's public key.

### 3. Proof signing input

The SDK generates the new key set next to the current one ([two-phase key replacement](../adr/0005-two-phase-key-replacement.md)) and signs, with the recovered private key `d` (ECDSA P-256 / SHA-256, DER):

```text
NEXUS-SIGN/RECOVERY-PROOF/v2
<sessionId>
<nonce, base64, exactly as received>
<nexusId>
<hex SHA-256 of SPKI(new signing public key)>
```

Lines are joined with `\n`, UTF-8, no trailing newline. The proof is bound to this session and to the new signing key: it cannot be replayed in another session or attached to another device's key.

### 4. Completion

`POST /v1/recovery/sessions/{sessionId}/complete` with `Authorization: Bearer <accessToken>`:

```json
{ "proof": "<DER, base64>", "newPublicKeyPem": "…", "platform": "IOS", "securityLevel": "…",
  "authPublicKeyPem": "…", "offlinePublicKeyPem": "…", "deviceAttestation": { … } }
```

`authPublicKeyPem` is required (400 without it).

Auth Core checks, in this order:

1. A bearer token is present (401 otherwise); the body and the session ID are well formed.
2. The session exists, is not used or expired, and the token hash matches (404 otherwise).
3. The device attestation verifies against the session nonce and the three new public keys ([session-bound attestation](../security/attestation.md#session-bound-attestation)) and comes from the claimed platform. With `REQUIRE_VALID_ATTESTATION=true` a failure is 403. This step does not count as an attempt.
4. In one transaction, with the session row locked: the session is re-checked, and refused (404) once it has had 5 attempts.
5. The identity is `ACTIVE` and its bank client is `ACTIVE` (409 otherwise); its recovery protocol is the session's, and protocol 1 is refused with 409 `RECOVERY_PROTOCOL_RETIRED`.
6. The phrase has not been used: no completed recovery of this identity since the recovery configuration was stored (409 `RECOVERY_PHRASE_USED` otherwise; the same check runs when the bank opens a session).
7. The stored recovery public key and wrapped key pass the [integrity check](#integrity-check) (sealed, this identity's, matching, latest record). Otherwise 409 `RECOVERY_INTEGRITY` and audit event `integrity_violation`; the attempt is not counted.
8. The proof verifies over the proof signing input with the stored recovery public key.
9. The attempt is counted (`attempt_count`, and `failed_attempt_count` for a failure). A failed proof is committed with audit event `recovery_failed` and answered 401; the SDKs report it as a wrong phrase.

A valid proof completes the recovery in the same transaction:

- a `SECURITY` notice (`PUSH_REPLACEMENT_TITLE`, `PUSH_REPLACEMENT_BODY`) is queued for the old device, when push mode is `NEXUS`, `PUSH_DELIVERY_ENABLED` is on and the old device has a push registration, as for a [device replacement](../architecture/device-replacement.md#push-notice);
- the identity's `ACTIVE` credential is revoked;
- the identity's `PENDING_USER` authorizations are cancelled;
- push registrations of the revoked credentials are removed, except one that still has the notice to deliver;
- the new credential is registered `ACTIVE`, with the next key version, and its keys and attestation material are sealed in a `CREDENTIAL_ENROLLED` record with reason `RECOVERY`;
- the session is marked used;
- audit events `credential_revoked`, `credential_created`, `recovery_completed`; webhook `identity.recovered` (`nexusId`, `newCredentialId`, `revokedCredentialIds`).

The response is 200 with `nexusId`, `credentialId`, `keyVersion`, `offlineServerPublicKeyPem` and `requestAuthentication: DEVICE_SIGNATURE`; no access token is issued.

A phrase recovers the identity once (audit finding A2-02). After a recovery, the bank's next `POST /v1/recovery/sessions` for the identity, and the completion of any session opened before it, answer 409 `RECOVERY_PHRASE_USED` until the recovered device sets up a new phrase (`POST /v1/mobile/recovery/setup`). Before this change the same phrase recovered the identity again, so a phished phrase could take the identity back each time the owner recovered it.

## Attempt limits and lockout

| Limit | Rule | Effect |
|---|---|---|
| Per session | 5 attempts (`recovery_sessions.attempt_count`) | Further completions of the session answer 404 |
| Per identity | Sum of `failed_attempt_count` over the identity's sessions created in the last 24 hours | At 10 or more, new sessions are refused with 409 `RECOVERY_LOCKED` |

The identity limit is checked when the bank opens a session. Sessions opened before the limit was reached keep their own 5 attempts until they expire. Recovery becomes possible again when failed sessions are older than 24 hours; [recovery lockout runbook](../operations/runbooks/recovery-lockout.md).

In protocol 2 these limits are defence in depth. A wrong phrase never reaches Auth Core, and a proof cannot be produced without the recovery private key, so failed proofs indicate a defective or hostile client rather than a customer mistyping the phrase.

## Protocol 1

Protocol 1 was removed in 2.0.0-rc.2. Identities set up before release 2.0 keep `recovery_protocol = 1` (set by migration 015), but migration 018 drops the stored verifiers (`nexus_identities.recovery_verifier`), so no protocol 1 secret remains.

- `POST /v1/mobile/recovery/setup` accepts only protocol 2.
- `POST /v1/recovery/sessions` and recovery completion for a protocol 1 identity always answer 409 `RECOVERY_PROTOCOL_RETIRED`. The customer sets up a new phrase on the enrolled device, or the bank uses [device replacement](../architecture/device-replacement.md).

## What Auth Core stores

| Where | Content |
|---|---|
| `nexus_identities` | `recovery_protocol` (2), `recovery_public_key_pem`, `recovery_wrapped_key` (60 bytes), `recovery_kdf_salt`, `recovery_kdf_iterations`, `recovery_updated_at`, `recovery_evidence_id` |
| Redis `recovery_setup:<credentialId>` | The issued setup salt, 600 s, removed on use |
| `recovery_sessions` | Session ID, identity, bank client, nonce and its hash, salt, SHA-256 of the access token, expiry, protocol, `attempt_count`, `failed_attempt_count`, `created_at`, `used_at` |
| `evidence_records` (`RECOVERY_CONFIGURED`) | `credentialId` of the device that registered the key, `configuredAt`, `recoveryProtocol`, `recoveryPublicKeyPem`, `wrappedRecoveryKeySha256`, `kdfSaltB64`, `kdfIterations`, sealed by the HSM ([evidence format](evidence-format.md)) |

Auth Core never receives the phrase, the seed, the wrapping key or the recovery private key.

## Threat analysis

| Party | Can | Cannot |
|---|---|---|
| Reader of the database or a backup | Read the recovery public key, the wrapped key, the salt and the iteration count, and search the phrase offline ([residual risks](#residual-risks)) | Complete a recovery: a proof needs the recovery private key. Learn the phrase from any stored value other than by that search |
| Writer of the database (application role) | Change stored recovery values, which makes session creation fail with `RECOVERY_INTEGRITY` (a denial of recovery, audited as `integrity_violation`). |  Substitute their own recovery key: it is not in a sealed record. Restore an earlier configuration with its record: only the latest record is accepted. Change the salt or iteration count handed to the device: they must equal the sealed ones. Detach the sealed record (`recovery_evidence_id` cannot be set back to `NULL`, migration 017). Reset the per-session or per-identity limits: attempt counters only grow and sessions cannot be deleted or extended (`recovery_session_lifecycle` and `refuse_delete()` triggers, migration 017) |
| Bank backend | Open a recovery session and so obtain the same material as a database reader, plus a nonce and an access token. Enrol a new device for the identity without the phrase through [device replacement](../architecture/device-replacement.md) | Complete a recovery without the phrase |
| Holder of a stolen recovery session (access token and response) | Use up to 5 attempts within 600 s; search the phrase offline from the wrapped key | Complete the recovery without the phrase. With `REQUIRE_VALID_ATTESTATION=true`, complete it from anything but a genuine instance of the bank's app on a genuine device, even with the phrase |
| Holder of the phrase alone | Nothing, until the bank opens a session | Open a session: only the bank backend can |
| Malware with the device's request-signing key | Request setup parameters | Register a new recovery key: setup needs a signature by the biometric signing key |

### Residual risks

- **Offline search of the phrase.** Anyone with the wrapped key, the salt and the iteration count (database or backup readers, the bank backend, the holder of a session response) can test phrase guesses offline: a correct guess opens the GCM tag. Neither the per-session nor the per-identity limit applies to this search. For a phrase generated by the SDK the search space is 2^128 (12 words carry 128 bits of entropy; the checksum is derived from them), so the expected cost is 2^127 guesses, each one PBKDF2-HMAC-SHA256 with 210 000 iterations (about 2^17.7 HMAC-SHA256 computations), followed by HKDF and one AES-GCM tag check: about 2^144.7 HMAC-SHA256 computations in total. The per-identity salt prevents one computation from serving several identities. These figures hold only for a phrase from the SDK's generator; Auth Core cannot check how the phrase behind a wrapped key was produced, so a modified client could register a key wrapped under a weak phrase.
- **Phrase disclosure.** Whoever learns the phrase, and obtains a session from the bank, takes over the identity. The bank's re-identification before opening a session is the control.
- **The bank can replace the device.** Device replacement enrols a new device after the bank's own re-identification, without the phrase. Recovery protects against Auth Core and its database, not against the bank.
- **Other new keys.** The proof covers the new signing key. The new authentication and offline keys are bound to the session by the device attestation, which is enforced only with `REQUIRE_VALID_ATTESTATION=true`.
- **Recovery key in app memory.** During setup and recovery the recovery private key is in the app's memory, not in secure hardware.

## Test vectors

`auth-core/test-vectors/recovery-v2.json` is generated by `generate-recovery-vectors.mjs` with Node.js crypto, independently of the server code. It holds a fixed phrase (the BIP-39 test mnemonic), salt, `nexusId`, credential ID, recovery scalar and IV, and the expected seed, wrapping key, associated data, wrapped key, setup signing input, proof signing input and a DER proof signature, plus two negative cases (a wrong last word, another `nexusId` in the associated data). The vectors use 1000 PBKDF2 iterations to keep tests fast; deployments use 210 000.

| Suite | Checks against the vectors | Where it runs |
|---|---|---|
| `auth-core/test/recovery-vectors.test.mjs` | The server's associated data, setup and proof signing inputs; the vector proof verifies; the wrapped key opens with the phrase and not with the wrong phrase | `auth-core` unit tests |
| `ios-sdk/Tests/NEXUSSignTests/RecoveryProtocolTests.swift` | Seed and wrapping key; wrapping with the vector IV reproduces the wrapped key and unwraps; wrong phrase and other identity fail with `invalidRecoveryPhrase`; signing inputs; the vector proof verifies; a fresh key round-trips; phrase normalization and checksum | CI job `ios-sdk / build and unit tests` (needs a Swift toolchain) |
| `android-sdk/src/test/kotlin/com/nexis/nexussign/RecoveryProtocolTest.kt` | The same as iOS, plus the scalar encoding of a fresh key and phrase normalization against the protocol 1 vectors | CI job `android-sdk / build and unit tests` (needs Gradle) |

End to end, `auth-core/test/integration/recovery.test.mjs` covers setup and recovery, that the database content alone cannot complete a recovery, the binding of the proof to the new key, a substituted recovery key, the issued salt and the biometric signature at setup, the identity lockout and protocol 1 refusal. The biometric prompt around setup and the SDKs' recovery flows on phones are not covered by these suites; they can only be verified on physical devices, which has not been done yet ([device acceptance checklist](../engineering/DEVICE_ACCEPTANCE_CHECKLIST.md)).
