## 2. Граница доверия: что может полностью скомпрометированный Auth Core

Модель: атакующий управляет Auth Core целиком — кодом, БД на правах владельца и HSM-сессией. Под контролем банка остаются его backend, учёт устройств, ключ доверия, закреплённые ключи доказательств и сохранённые heads. Под контролем клиента — устройство и банковское приложение.

Проверено тестом `bank-trust-compromise.test.mjs`. «Атакующим» выступает собранный код самого Auth Core (`createCredential`, `sealCredentialEnrolment`), запущенный с его конфигурацией и тем же токеном SoftHSM (`test/integration/support/compromise.mjs`).

| Сможет ли Auth Core самостоятельно … | Результат |
|---|---|
| 1. создать регистрацию нового credential (без токена банка, с выдуманной авторизацией замены, с «подтверждённой» аттестацией) | **да** |
| 2. запечатать её действительной HSM-печатью | **да**, настоящим ключом доказательств |
| 3. принять подпись подтверждения этим ключом | **да** |
| 4. выдать `VERIFIED`, `confirmed: true` и принять commit-запрос (202) | **да** |
| 5. сформировать экспорт, который verifier принимает с закреплёнными ключами | **да** |
| … заставить банк исполнить операцию | **нет, если банк выполняет собственную проверку** (раздел 4) |

Пять свойств различаются и друг друга не заменяют:

| Свойство | Кто устанавливает |
|---|---|
| криптографическая корректность подписи | любой (verifier) |
| целостность доказательства | любой, у кого есть закреплённые ключи доказательств |
| достоверность регистрации устройства | банк: отпечаток, сообщённый его приложением по его каналу, совпадает с запечатанным ключом |
| разрешение банка доверять устройству | банк: одобрение, подписанное его ключом доверия, без отзыва |
| разрешение исполнить конкретную транзакцию | банк: решение, включая сверку условий с собственным запросом |

## 4. Исправленные дефекты и доказательства

Выбранный механизм — **bank credential trust v1** (D-041, `docs/protocol/bank-credential-trust-v1.md`). Сравнены четыре варианта:

1. **Auth Core проверяет одобрение банка.** Не выбран: проверка выполнялась бы внутри скомпрометированного компонента и вдобавок потребовала бы API и миграции.
2. **Контрподпись банка в цепочке.** Не нужна: её всё равно проверяет банк, а формат пришлось бы менять.
3. **Подписанное банком одобрение `(nexusId, credentialId, отпечаток ключа)` в реестре банка и решение банка об исполнении.** Выбран.
4. **Закрепление ключей и heads вне Auth Core.** Уже существовало; теперь закреплённые ключи стали обязательными для решения.

Протокол устройства и Auth Core не менялись.

| Исправление | Коммит | Доказательство |
|---|---|---|
| V1, V2: `bankExecutionDecision` (`auth-core/scripts/lib/bankTrust.mjs`) — решение банка. Требует закреплённые ключи доказательств (ключи из экспорта не используются), сверяет условия с запросом банка, требует одобрение ключа его отпечатком, подписанное ключом доверия банка, для того же `nexusId`. Отказывает при отзыве в реестре банка и при любой непроверяемой записи реестра. С цепочкой проверяет одобрение каждой регистрации, наличие записи в цепочке и сохранённые heads. ## 7. Оставшиеся архитектурные риски

- **R-22.** Защита работает, только если банк действительно внедрит проверку и выполняет её до каждого исполнения, а ключ доверия, реестр, закреплённые ключи и heads хранит вне досягаемости Auth Core. В реальный backend банка проверка не встроена, demo bank её не выполняет.
- **R-23.** Отказ в обслуживании со стороны Auth Core. Аттестация устройства проверяется только Auth Core. Записи после последнего сохранённого банком head **не обнаруживаются**.
- **Компрометация самого backend банка или его приложения** — вне модели. Отпечаток ключа надёжен ровно настолько, насколько надёжно приложение банка.
- **iOS.** `signingKeyFingerprint()` и тест не скомпилированы; контроллер звонков на iOS (actor) не менялся и не запускался.
- **Прежние риски.** Нет нативных сборок и тестов на устройствах. Нет HSM поставщика. Нет lockfile, поэтому цепочка поставок не воспроизводима (FI-009). Независимого аудита нет. Юридическая приёмка не проведена.

## 8. Обязанности банка

1. Создать ключ доверия (ECDSA P-256) в собственном HSM и никогда не передавать его Auth Core.
2. Закрепить открытые ключи доказательств по протоколу key ceremony и при каждой ротации, вне Auth Core.
3. При регистрации, замене и восстановлении:
   - получить от своего приложения `credentialId` и `signingKeyFingerprint()`;
   - сверить отпечаток с ключом в записи `CREDENTIAL_ENROLLED`, проверенной закреплёнными ключами;
   - подписать одобрение; при замене и восстановлении отозвать прежние credential в своём реестре.
4. При утере устройства или закрытии — сначала отзыв в своём реестре, затем отзыв в Auth Core.
5. Сохранять head из каждого `evidence.appended`.
6. Перед каждым исполнением запускать `bankExecutionDecision` / `bank-execution-check.mjs` с закреплёнными ключами, реестром, ожидаемыми условиями и цепочкой. Исполнять только при положительном решении: `VERIFIED`, `confirmed: true` и 202 входными данными не являются. При отказе отправить `bank-commit-result CANCELLED` и разбирать случай как инцидент.
7. Однократность движения денег по `bankTransactionReference` обеспечивает банк.
